# План пилота — Трек A «Пилот у владельца» (meeting-first)

> **Дата**: 2026-11-14 | **Статус**: утверждён пользователем, ожидает данные от владельца
> **Основание**: встреча 2026-11-11 (`inputs/transcripts/Meet_2026-11-11_Automation.md`), решение в `reports/DECISION_LOG.md`

---

## 1. Цель

Доказать экономию в рублях на **реальных данных** владельца по двум задачам, взятым на встрече:

1. **Оптимизация обеспечения заказа** — себестоимость: закупки, инструмент, режимы, make-or-buy.
2. **Синхронизация отделов** — ликвидировать невидимые задержки на стыках («заказ взяли, металл 2 недели не куплен»).

Промышленная ОС v2.0 (`docs/plans/2026-11-14-industrial-intelligence-architecture.md`) — **дорожная карта после пилота**, не текущий скоуп. Founder-пайплайн (`founder/`) заморожен до валидации у реального покупателя; его инструменты используются для упаковки оффера.

## 3. MVP-1 «Закупки и тендеры» (2 недели после получения данных)

**Вход**: тендерная выгрузка (п.1 запроса), прайсы поставщиков (п.5), исторические заказы (п.4).

**Шаги**:
1. Нормализация выгрузки: единый справочник марок стали / профилей / диаметров.
2. Ретроспектива проигранных тендеров: дельта до цены победителя, декомпозиция «материал / логистика / маржа» — где именно проигрываем.
3. Агрегация потребности по маркам и диаметрам across заказов → кандидаты в оптовые пулы (критерии из спеки).
4. Расчёт экономии: оптовая цена vs розничная + одна доставка vs несколько; сезонность (закупка до весеннего роста цен), неликвиды/аукционы как отдельный канал.
5. Отчёт владельцу: пулы с суммами экономии, топ проигранных тендеров с разбором, рекомендации по закупочному календарю.

**Критерий успеха**: найдены и количественно подтверждены пулы/меры с экономией в рублях на горизонте месяца. Ориентир 7–15% на сырье — **гипотеза из спеки, проверяется на данных**, не обещание.

## 4. MVP-2 «Цифровой бегунок» (2 недели, старт со 2-й недели MVP-1)

**Вход**: 3–5 живых заказов (п.2), контакты ответственных (п.3), нормативы SLA из интервью на визите.

**Шаги**:
1. Карточки заказов в vault по `06_Шаблоны/Шаблон_Заказа.md`; статусы вводит офис (цех не трогаем — там бумага).
2. Гармонизация контракта статусов (см. §6) + timestamps переходов.
3. Dataview-пульт SLA: заказы с превышением норматива перехода (M1–M6 из спеки) подсвечиваются в день возникновения.
4. Алерты: напоминание исполнителю → эскалация руководителю отдела → сводка владельцу. Канал: Telegram (или почта — уточнить на визите).
5. Журнал потерь: каждая эскалация фиксируется с экономическим риском (неустойка, простой).

**Критерий успеха**: ни один заказ пилота не «забыт»; все задержки сверх SLA видны в день возникновения; владелец получает сводку без ручного сбора статусов.

## 5. Зависимости и риски

| Риск | Митигация |
|---|---|
| Данные не дают / дают поздно | Шаг 0 письмо + минимальный набор (п.1–3); визит как альтернативный канал сбора |
| Сопротивление отделов | Работаем на уровне офиса, не заменяем людей (решение DECISION_LOG); интервью с начальниками цехов лично |
| Качество выгрузок низкое | Ретроспектива MVP-1 сама покажет пробелы; обезличивание чувствительных полей |
| Конфиденциальность | Локальный контур обработки, без облака; NDA; зафиксировать в спеках отдельным разделом |
| Два агента пишут в один репо | Координация: разные ветки/worktree, коммиты малыми порциями |

## 6. Технические долги, закрыть до MVP-2

- **Контракт статусов расходится**: шаблон vault (8 статусов) vs `digital_thread_order.schema.json` (12) vs спека Order Controller (M1–M6) vs шаблон (M1–M7). Привести к единому контракту; владелецvault-сессии — согласовать.
- Локальный LLM-контур для чувствительных данных не специфицирован — добавить раздел в спеки до обработки реальных данных.
- CFO-модель (`founder/numbers.json`) не верифицирована — коммерческие условия пилота обсуждать с владельцем лично после диагностики, не опираться на модельные цифры.

## 7. Коммерческая рамка

Формат пилота обсуждается после диагностики (ориентир из idea v2.0: пилотный контракт 150 тыс. ₽/мес — непроверенная гипотеза). Возможные рамки: фикс за пилот, success fee от подтверждённой экономии, гибрид. Решение — за владельцем по факту отчёта MVP-1.

## 8. Следующие шаги (по порядку)

1. Пользователь проверяет и отправляет письмо (`reports/owner_email_draft.md`) + запрос данных.
2. Согласовать визит на производство (1 день) и знакомство с технологом / начальниками цехов.
3. Получить минимальный набор данных → старт MVP-1.
4. Дизайн-трек параллельно: service blueprint цепочки заказа + концепт пульта диспетчера (роль пользователя как дизайнера).
5. После отчёта MVP-1: решение о коммерческих условиях и фазе 2 (Cost Engineer).
