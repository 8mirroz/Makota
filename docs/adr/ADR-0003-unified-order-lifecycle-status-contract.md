# ADR-0003: Единый контракт статусов жизненного цикла заказа и приоритет меток времени SLA

## Status

Accepted (2026-11-18)

## Context

В ранней версии системы существовало расхождение между тремя представлениями жизненного цикла заказа:
1. Карточки заказов в Obsidian Vault (`06_Шаблоны/Шаблон_Заказа.md`) использовали 8 русскоязычных статусов.
2. Контроллер SLA (`engine/order_sla_tracker.py`) оперировал 7 англоязычными ключами (`01_lead_quoting` .. `07_dispatch`).
3. Схема Digital Thread (`specs/schemas/digital_thread_order.schema.json`) содержала 12 детализированных статусов по ISO 23247.

Дополнительно отсутствие отдельного поля времени входа на текущий этап (`stage_entered_at`) приводило к расчёту длительности этапа от даты создания заказа (`created_at`), порождая ложные критические SLA-алерты (192+ часов) для заказов, штатно находящихся в производстве.

## Decision

1. Утвердить `docs/contracts/status_contract.md` в качестве единого источника истины (SOT) для маппинга статусов заказа.
2. Реализовать в `OrderSLATracker` двусторонне совместимый словарь `STAGE_ALIASES` (поддерживающий русские ключи Vault, полные статусы JSON Schema и legacy-ключи SLA) и множество терминальных статусов `TERMINAL_STAGES` (`09_закрыт_прибыль_зафиксирована`, `11_закрыт_прибыль_зафиксирована`, `99_отменен`, `99_отменен_проигран`), которые никогда не генерируют алертов просрочки.
3. Установить в `engine/vault_parser.py` строгий приоритет чтения метки времени входа на этап:
   $$\text{stage\_entered\_at} \to \text{updated\_at} \to \text{created\_at}$$
4. Включить поле `stage_entered_at` в шаблон `06_Шаблоны/Шаблон_Заказа.md`, карточки активных заказов и JSON Schema `specs/schemas/digital_thread_order.schema.json`.

## Consequences

- **Позитивные**: Полностью устранены ложные срабатывания SLA по заказам в работе (например, `MKT-2026-084` на токарном ЧПУ); обеспечена 100% обратная совместимость со старыми тестами и карточками; автоматическая контрактная валидация карточек через `validate_vault_order_frontmatter`.
- **Ограничения**: При ручной смене статуса заказа в Obsidian менеджеру рекомендуется обновлять `stage_entered_at` (или использовать автоматический триггер обновления даты).

## Rollback

Откат возможен через `git revert` коммита контракта; благодаря fallback-цепочке `stage_entered_at -> updated_at -> created_at` удаление поля `stage_entered_at` из карточек не нарушает работоспособность парсера.

## Validation

- Автоматические тесты `test_all_active_vault_orders_conform_to_contract` и `test_stage_entered_at_priority_eliminates_false_sla_breach` в `tests/test_vault_runner.py`.
